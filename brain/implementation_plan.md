# Phase 2: Zero-Shot TTS Architecture Integration

This phase connects the Audio-JEPA Context Encoder (from Phase 1) with the FastPitch TTS Decoder to achieve zero-shot voice cloning capabilities.

## User Review Required

> [!WARNING]
> Please review the architecture changes proposed below. This will fundamentally connect the Phase 1 work into the final TTS application architecture.

## Open Questions

> [!IMPORTANT]
> 1. **Context Window Strategy**: For the Context Encoder to extract a speaker's fingerprint, do we want to provide it with exactly 3 seconds of reference audio, or a variable length? 3 seconds is standard for zero-shot TTS cloning, but we can configure it.
> 2. **Decoder Choice**: I've selected `FastPitch` from the `tts-arabic-pytorch` repository. It is a highly parallel, non-autoregressive architecture that produces very high-quality speech and trains much faster than `Tacotron2`. Does this sound good to you?

## Proposed Changes

We will create a new top-level architecture module that orchestrates the data flow between the Audio-JEPA Context Encoder and the FastPitch Decoder.

### 1. The Top-Level Wrapper (ZeroShotTTS)
We will create a new Lightning Module `ZeroShotTTS` that houses both components:
- **Context Encoder**: The Audio-JEPA encoder network.
- **Embedding Projector**: A small linear layer that maps the high-dimensional Audio-JEPA embedding (e.g., 1024) down to the FastPitch speaker embedding dimension (e.g., 384).
- **TTS Decoder**: The FastPitch network.

### 2. Modifying FastPitch Decoder
We will patch `tts-arabic-pytorch/models/fastpitch/fastpitch/model.py`. 
Currently, FastPitch expects a discrete integer ID for the speaker (`speaker_id = 5`) and looks it up in an internal embedding table. We will change the `forward()` method to directly accept the continuous `speaker_embedding` generated by the Context Encoder.

### 3. Modifying the Datasets
We will update `arabic_dataset.py` to yield a new key: `reference_audio`. 
During training, we will use the `client_id` from the Hugging Face dataset to randomly pick a different 3-second audio clip from the *same* speaker to serve as the reference audio. The Context Encoder processes this `reference_audio` to extract the fingerprint, while the FastPitch decoder uses the text to reconstruct the `target_audio`.

Do you want to keep it frozen for the entire initial run, or do you want to implement a gradual unfreezing callback?

## Proposed Changes

### 1. PyTorch Lightning DataModule Updates
- Update `src/data/arabic_datamodule.py` (or create `zero_shot_datamodule.py`) to properly format batches. We need to ensure that the DataLoader collate function (`TTSCollate`) properly batches the text, mel targets, and reference audio spectrograms together.

### 2. Loss Function Integration
- In `ZeroShotTTS`, integrate the `FastPitchLoss` module (from `tts-arabic-pytorch/models/fastpitch/fastpitch/loss_function.py`) to correctly compute the loss (Mel reconstruction + Pitch + Duration).

### 3. Training Script
- Create a new `train_zero_shot.py` (or PowerShell script) that initializes the `ZeroShotTTS` model, the `DataModule`, and the `lightning.Trainer()`, then calls `trainer.fit(model, datamodule)`.
